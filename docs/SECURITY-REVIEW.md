# Delbert - Security review (2026-11-02)

A first, partial review of the security-critical paths, done by reading the code and writing adversarial tests against a real PostgreSQL. It is **not** an independent audit: a human reviewer should repeat it, especially on the areas listed under "Not reviewed". Severity is the author's estimate for a deployment as documented.

## Findings

| Id | Severity | Finding | Status |
|----|----------|---------|--------|
| F-01 | High | The audit hash chain verified cleanly after the newest events were deleted, or after the whole history was erased and rewritten through the normal append path (every hash valid). A database administrator, or a compromised Core with a privileged connection, could remove evidence undetected. | **Fixed**: signed anchors (migration `0026`), see [API.md](API.md) "Audit anchors". Tests: `tests/audit_adversarial.rs` |
| F-02 | Medium | `POST /v1/enroll` and `POST /v1/proxies/enroll` answered a bad, expired, revoked or exhausted key with 401 but recorded **nothing**: no audit event, no throttling. Guessing a 256-bit key is infeasible, but failed attempts are exactly what NIS2 incident detection needs; auditing them naively would let an anonymous caller grow the append-only trail. | **Fixed** (2026-11-02, migration `0027`): 10 failures per address (or per proxy) in 10 minutes, then 429 before the key is looked at; failures are audited (`enroll.denied`, the key itself never) up to that ceiling per address and 200 overall per window, a throttled address once (`enroll.throttled`). Tests: `tests/enroll_throttle.rs` |
| F-03 | Medium | The anchors are stored in the same database they protect. They detect truncation and rewriting of anchored history, but whoever can delete the newest anchors *and* the newest events is only detectable against a copy kept elsewhere. | **Mitigated** (2026-11-02): every anchor is logged as a structured line (`audit.anchor`) and appended to `DELBERT_AUDIT_ANCHOR_FILE` when set; `delbert-sign verify-anchors` checks such a copy without the database, also against an audit export. It still depends on the operator putting the file/log on storage the database administrators cannot write. A console view of the anchors is not done |
| F-04 | Low | Anchors were signed with the policy-signing key (separate signature domain `delbert-audit-anchor-v1`, so no cross-use). A dedicated audit key limits the damage of one key leaking and allows a different custody. | **Fixed** (2026-11-02): optional `DELBERT_AUDIT_SIGNING_KEY_FILE` / `DELBERT_AUDIT_SIGNING_KID` (must differ from the policy key); anchors signed earlier with the policy key keep verifying. Test: `a_dedicated_audit_key_signs_anchors_and_older_ones_still_verify` |
| F-05 | Low | Signed requests carried a timestamp and a nonce, but the Core kept no nonce cache: a captured proof could be replayed within the 60 s window. | **Fixed** for the requests an agent builds afresh at every attempt (policy pull, renewal, artifact download, delivery bundle): `replay.rs`, accepted once per agent. **Not** applied to reports and event batches: they are idempotent (ordered by their own timestamp, events carry ids) and a proxy legitimately forwards the same proof again on a retry. The cache is per Core process and bounded (full of fresh entries: accepts rather than locks agents out). Test: `tests/replay.rs` |
| F-06 | Low | An enrollment key was tenant-wide: its holder could claim any pre-created, not yet enrolled agent name of the tenant. | **Fixed** (2026-11-02, migration `0028`): a key can be bound to one agent name (`agent_name`); any other name is refused like a bad key and counts as a failure. Binding is optional (recommended). Test: `a_key_bound_to_a_name_enrolls_only_that_agent` |
| F-07 | Info | The authorization callout does not verify the signature of the request JWT it receives on `$SYS.REQ.USER.AUTH`; it relies on NATS permissions keeping every client away from that subject. Verifying against the `iss` inside the request proves nothing (an attacker would sign with their own key): it needs the NATS server's public nkey **pinned** in the Core's configuration, plus `xkey` encryption of the callout messages (already on the roadmap). Not done: it needs a NATS server in the test environment, which this review did not have. | Open (hardening) |
| F-09 | Medium | With `DELBERT_TRUST_FORWARDED=true` the client address was the **first** entry of `X-Forwarded-For`, which the client controls when the reverse proxy appends instead of overwriting the header: the login and enrollment throttles could be sidestepped by rotating the header, and free-form text ended up in throttle keys and audit details. | **Fixed** (2026-11-02): the entry `DELBERT_TRUST_FORWARDED_HOPS` from the right is used (default 1), it must be an IP address, otherwise the connection's address is used. Tests: `auth::client_address_tests`, `tests/enroll_throttle.rs` |
| F-08 | Info | `cargo audit` / `cargo deny` were not run. | **Done** (2026-11-02): `cargo audit` ran against the RustSec database: 7 advisories, all reviewed and none reachable in Delbert's use (build-time `zip`, S3 XML parsing, RSA verification only), recorded with reasons in `.cargo/audit.toml`; new ones fail the `audit` workflow (also weekly). `cargo deny` (licences, duplicate/banned crates) not set up |
| F-10 | Medium | **Found by fuzzing the policy parser:** the YAML parser (`serde_yaml_ng` on `unsafe-libyaml`) takes time *quadratic* in the nesting of flow collections. Measured in a release build: 80 KB of `[` kept a core busy for 15 s, 320 KB of `{a: ` for 37 s; with the default 2 MiB request body one authenticated request (`policies:write`, or the validate endpoint) could stall a Core worker for minutes, and a few of them the whole Core, across tenants. The same parser reads files of content sources (git), so a repository could do it too. | **Fixed** (2026-11-02): `delbert_policy::guard_yaml` refuses, before parsing, a document with more than 2000 `[` or `{` characters (422 "YAML too complex"; real files have a handful, large inline text belongs in an artifact), at most ~10 ms of work at the limit. Applied by `from_yaml` and `parse_yaml`, which also read repository variables and tenant files. Tests: `delbert-policy/tests/robustness.rs` (nesting, alias bombs, huge scalars, odd tokens, 3000 seeded mutants of a valid policy), `delbert-pki/tests/robustness.rs` (mutated CSRs and certificates; a CSR cannot choose its identity), `core/tests/hostile_input.rs`. **Residual:** `unsafe-libyaml` is unmaintained (RUSTSEC-2024-0449) and contains `unsafe` the workspace lint does not cover; follow a maintained parser. Artifact names, hashes and sizes were tested too (F-11) |
| F-11 | Low | **Found by the hostile-input tests:** a NUL byte in a name (`PUT /artifacts/a%00b`, and in general any text or JSON value) reached PostgreSQL, which cannot store it, and the Core answered **500** with an error log line each time. No data leaked, but it is a trivial way to fill the logs and to trip 5xx alerting. | **Fixed** (2026-11-02): database errors 22021 / 22P05 map to 422 for every endpoint, including the audit writer. Tests: `tests/hostile_input.rs` (20 entry points: paths, queries, JSON bodies), `tests/hostile_artifacts.rs` (crafted names and hashes cannot leave the tenant namespace or the store; 64 MiB limit holds, 413) |
| F-12 | Medium | **Found while preparing the ASVS checklist:** template evaluation (MiniJinja) had no resource limit. `{% for a in range(100000) %}{% for b in range(100000) %}{% endfor %}{% endfor %}` never finished (measured, > 8 s and unbounded), in the Core's render preview (a request thread) and, worse, on an **agent** applying a tenant's policy on a managed host: one template could freeze a host's convergence. The same held for `when` expressions. | **Fixed** (2026-11-02): all evaluations go through `delbert_policy::template_env()`, which sets a fuel limit (`TEMPLATE_FUEL`, 5 million instructions: well under a second) and strict undefined variables. Tests: `delbert-policy/tests/templates.rs` |
| F-13 | Low | The Core API sent no `Cache-Control`, `X-Content-Type-Options` or framing headers (the console did). Token lists, secret names and the audit trail could be cached by an intermediary. | **Fixed** (2026-11-02): every API answer carries `no-store`, `nosniff`, `no-referrer` and a restrictive CSP; the Swagger UI is left alone. Test: `api_answers_carry_security_headers` |

## Checked and found sound

- **Audit trail**: events are written in the same transaction as the change; appends are serialized by an advisory lock; update/delete/truncate are blocked by triggers *and* not granted to the runtime role (`0005`, `0026`). The only residual weakness was F-01.
- **Tenant isolation** (`tests/tenant_isolation.rs`): a tenant-admin and an operator of tenant A, against every tenant-scoped route of tenant B (17 reads, 12 writes): every answer is 404/405 or 403, nothing changes, the tenant list shows only A, platform routes (`/v1/users`, `/v1/proxies`, SSO, audit verify/anchors) are refused. An auditor scoped to A sees only A's events in the list and in the export. Note that the Json body is parsed before authorization (a wrong body gets 422 before 404); it leaks nothing but the shape of the route.
- **Names in bus subjects**: tenant and agent names cannot contain dots, wildcards, separators or spaces (a test covers it), so the per-agent subject permissions cannot be widened or shifted.
- **Enrollment**: the key is stored as SHA-256 of 256 random bits, looked up with `FOR UPDATE` (no over-use under concurrency), one answer for every kind of invalid key (no oracle), the certificate subject is chosen by the Core, not by the CSR.
- **Callout**: the certificate must carry exactly the public key on record for that tenant/agent (current or previous during a renewal), so deleted or rotated agents are refused and a certificate alone, without the key, is useless; permissions are confined to the agent's own subjects (unit-tested); sessions expire and are re-authorized.
- **Policy signing**: Ed25519 over JCS, verified strictly on the agent (see [ROTATION.md](ROTATION.md)); the new detached-signature API is domain-separated.

## Against a standard

[ASVS.md](ASVS.md) maps the product to OWASP ASVS 4.0.3 level 2 chapter by chapter, with its own prioritized gap list (SSRF filter, self-service password change, a security log for access-control failures, rate limiting, signed images and an SBOM, among others).

## Not reviewed

Needs a human reviewer, in this order: the agent's apply path (symlinks, ownership and modes of managed files, `package`/`service` arguments), `auth.rs` (sessions, MFA, throttling, API tokens), SSO and the BFF in `web/`, content sources (git, path handling of the editor's commits), artifact and secret handling, the proxy (store-and-forward, enrollment relay), the Operator's RBAC and its use of Secrets, container image hardening and dependencies (F-08). Also useful: fuzzing the YAML policy parser, the CSR parser and the artifact upload.
